# Task Management API — Project Overview

> Generated by docpilot from source: `task-management-api/`

## What This Project Does

A RESTful task management API built with FastAPI. Users register, authenticate via JWT, and perform CRUD operations on their own tasks. Tasks have a status lifecycle (`pending` → `in_progress` → `done` / `cancelled`). Data is persisted in a local SQLite database via SQLAlchemy ORM.

**Data Flow:**
1. Request arrives at FastAPI router
2. FastAPI validates the JWT via `Depends(get_current_user)` in `auth.py`
3. Request body is parsed and validated by the Pydantic schema in `schemas.py`
4. Route handler calls the ORM layer (`models.py`) via an injected `db: Session`
5. SQLAlchemy translates operations to SQL and executes against `tasks.db`
6. Response is serialized through the `TaskResponse` Pydantic schema

## Module Structure

```
task-management-api/
├── main.py              # FastAPI app instance, startup events, router registration
├── database.py          # SQLAlchemy engine, SessionLocal factory, Base, get_db dependency
├── models.py            # SQLAlchemy ORM models: User, Task

└── routers/
    └── tasks.py         # CRUD route handlers for /tasks endpoints
```

### Module Responsibilities

| Module | Responsibility |
|--------|---------------|
| `main.py` | Creates the `FastAPI()` app, registers routers, runs `create_all()` on startup |
| `database.py` | Defines `engine` (SQLite), `SessionLocal`, declarative `Base`, and the `get_db()` generator dependency |
| `models.py` | SQLAlchemy table definitions for `User` and `Task`; relationships between them |
| `schemas.py` | Pydantic V2 models for input validation and response serialization |
| `auth.py` | `create_access_token()`, `verify_password()`, `get_current_user()` FastAPI dependency |
| `routers/tasks.py` | The four task CRUD handlers; all routes require an authenticated user |

## Authentication Model

All task endpoints are protected. The API uses stateless JWT authentication:

- Tokens are issued by `POST /auth/token` (OAuth2 password flow)
- Tokens must be sent as `Authorization: Bearer <token>` on every request
- The `get_current_user` dependency in `auth.py` decodes the token and injects the current `User` into the route handler
- No refresh token mechanism was found in the source

> 🔴 **docpilot note:** User registration endpoint not found in `routers/` or `main.py`. It is unclear how new users are created — either there is a separate admin script, a not-yet-implemented `/auth/register` route, or users are seeded directly into the database. Confirm with the team.
