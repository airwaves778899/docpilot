## Installation

```bash
# 1. Clone the repository
git clone https://github.com/example/task-management-api.git
cd task-management-api

# 2. Create and activate a virtual environment (recommended)
python -m venv .venv
source .venv/bin/activate        # Linux / macOS
.venv\Scripts\activate           # Windows PowerShell

# 3. Install dependencies
pip install -r requirements.txt
```

## Running the Development Server

```bash
uvicorn main:app --reload
```

- The API will be available at `http://localhost:8000`
- `--reload` enables hot-reload on source changes (do not use in production)
- Interactive API docs: `http://localhost:8000/docs`

**The SQLite database (`tasks.db`) is created automatically on first run.** The application calls `Base.metadata.create_all(bind=engine)` in the `startup` event handler in `main.py`. No manual migration step is needed for a fresh install.

## Running in Production

```bash
# Use multiple workers for production; disable --reload
uvicorn main:app --host 0.0.0.0 --port 8000 --workers 4
```

> 🔴 **docpilot note:** SQLite is not suitable for a multi-worker or multi-process production deployment (concurrent writes will cause locking errors). If running with `--workers > 1`, the database backend should be replaced with PostgreSQL or MySQL via a compatible SQLAlchemy URL. No production database configuration was found in the repository.

## Database

The application uses SQLite by default. The database file (`tasks.db`) is created in the working directory on first run.

```
task-management-api/
└── tasks.db        ← auto-created; do not commit to version control
```

**Tables created on startup:**

| Table | Description |
|-------|-------------|
| `users` | Registered users (username + bcrypt hash) |
| `tasks` | Task records with status and owner reference |

> 🔴 **docpilot note:** No database migration tool (Alembic, etc.) was found in the repository. Schema changes made after the initial `create_all()` will not be applied to an existing `tasks.db` automatically. If the schema changes, the database must be deleted and recreated (losing all data) or migrations must be written manually. Consider adding Alembic for production use.
